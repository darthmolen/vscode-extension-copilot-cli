# Lane A → Lane B: addendum — ACP's real session vocabulary

**From:** Lane A (IN-3) · **2026-08-17** · Follows the checkpoint §5 response.

**Why now:** the earlier answer to your Q4 ("is the narrow-slice guard the right seam?") gave a
three-verb table. That was drawn from the ACP `.d.ts`. The SDK **source** has since been cloned into
`research/acp-sdk/` and the real surface is **eleven** methods, four of which collide with names you
are choosing this week. This is cheap to act on now and expensive after Task 5 reroutes 75 call

**Nothing here reverses the earlier advice.** The narrow slice is still right; the vocabulary is
wider than I said.

---

## 1. The real agent-side session surface

From `acp.methods.agent.session` (verified at runtime, SDK v1.3.0):

```
new · load · list · delete · fork · resume · close · setMode · setConfigOption · prompt · cancel
```

Four overlap concepts you are naming right now:

| ACP method | What Lane B currently calls it | Suggestion |
| --- | --- | --- |
| `session/close` | `disposeHost` / `disposeAll` | Consider `close()` on the host's public slice. `dispose()` is a VS Code idiom; `close` is the protocol's. |
| `session/list` | the registry's enumeration | Align the accessor name rather than inventing a third. |
| `session/set_mode` | plan-mode toggling | **Plan mode is a first-class ACP concept** (`SetSessionModeRequest: { sessionId, modeId }`). Worth knowing before modelling it as a bespoke flag. |
| `session/resume` *and* `session/load` | "resume" | These are **two distinct ACP methods**. Do not collapse them into one word. |

This is not a demand to rename anything — `dispose()` is idiomatic in an extension and may well be
the right public name. It is so the choice is deliberate rather than accidental, which is what Q4 was
actually asking.

## 2. The one that matters for Slice 3: **ACP's fork has no message boundary**

```
ForkSessionRequest:  [ sessionId, cwd, additionalDirectories, mcpServers, _meta ]
ForkSessionResponse: [ sessionId, modes, configOptions, _meta ]
```

**No `toEventId`, no message or event boundary of any kind.** ACP's `session/fork` forks a *whole*
session.

The Copilot SDK's `sessions.fork` **does** take `toEventId` — that is what S1 verified and what
Slice 3's fork-from-this-message depends on.

### What follows

1. **Slice 3 is not blocked.** Per-message fork lives below the protocol boundary, in our SDK layer,
   and v3.14.0 ships long before any of this crosses ACP.
2. **Do not assume ACP will one day carry it natively.** If per-message fork ever needs to cross the
   protocol it is `_meta` or a custom method — not `session/fork`.
3. **There are now three fork concepts.** Name them deliberately; they do not converge:

   | Fork | Boundary | Layer |
   | --- | --- | --- |
   | Copilot SDK `sessions.fork` | `toEventId` — exclusive | below us |
   | ACP `session/fork` | whole session only | protocol |
   | Lane B `SessionForkService` | `toEventId` + filesystem fallback | ours |

4. `SessionForkService` staying an **our-layer** concept is the right call, and this is the evidence
   for it: it is strictly richer than the protocol method of the same name.

## 3. Also worth knowing

- **`session/set_config_option`** exists alongside `set_mode` — if any of the slash-command settings
  are really per-session config, there is a protocol shape for them.
- **`client.fs.readTextFile` / `writeTextFile`** are real client-side methods an agent may call. They
  are gated by the `clientCapabilities.fs` flags, which is why Lane A defaults them to deny.
- **`elicitation/create`** — asking the user a structured question is a protocol concept, not
  something to invent.
- **`session/request_permission`** is the client-side permission prompt Lane A forwards to instead
  of the manager's hardcoded `approveAll`. **Unlike the `fs` methods above, it is not
  capability-gated** — sitting next to that bullet, this one used to read as though it were.
  `ClientCapabilities` has no permission-shaped field at all, and on the `Client` interface
  `requestPermission` is one of only two **non-optional** members. So a client does not opt in, and
  an agent does not check first: forwarding is unconditional. (Shipped 2026-08-19. What happens when
  the client cannot be reached is a separate question, answered by a deny fallback — see IN-3 §4.)
