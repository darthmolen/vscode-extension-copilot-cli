# v3.15.0 — the extension, driven by any ACP host

**Status:** **DECLINED 2026-08-22.** Not a release. Lane B's answer on cross-talk 02: *the ACP agent
gets a merge, not a version.* A version number is a promise to users, and `--acp` is a capability
nobody can reach. The agent merges to `main` after v3.13.0, unreleased, riding in the VSIX at zero
bytes. **The row becomes a version when it has a door** — the npm package with a `bin`, or IN-4
unblocking.

Kept because §3 is the packaging analysis whoever builds that door will need, and §0 records the
measurement that killed the premise. Do not execute §3 as a release plan.

**Lane:** A · `feature/4.0-in3-acp-server` · **Depends on:** v3.13.0 shipping first.

## 0. What changed, and what it costs this plan

Written before measuring, which is the error. `copilot --acp` is in the ACP Registry as
`@github/copilot@1.0.80`, auto-bumping hourly; we bundle 1.0.68. Probed side by side, upstream
advertises `authMethods` we do not (registry CI enforces it), `image` and `embeddedContext` where
ours are `false`, MCP capabilities, and three modes with canonical URI ids. We lead on
`session/fork`, `session/close` and `usage_update`.

Their plan mode is **one session** — measured on disk — so our context isolation is a real
difference, and it is the same design decision that produced the 197 `-plan` halves P4 exists to
clean up.

**§3 (packaging) is therefore on hold.** Publishing a near-duplicate that lags is worse than not
publishing. **§4 (what moves to 4.0) is unaffected** and was always the stronger half: IN-4 is
blocked on OUT-1 whatever we do about distribution.

**The open question, restated without the dead premise:** is there a version worth cutting for
*"the extension is portable and the v5.0 boundary is proven"*, with no external distribution — or
does this simply merge to `main` after v3.13.0 and wait for IN-4? Lane B's call; cross-talk 02.

## 1. Why this release exists

IN-3 is done and independently validated. On 2026-08-22 it drove **Zed** — a third-party editor whose
reading of ACP owes nothing to ours — through permissions (including a session-scoped grant), file
diffs, a native plan checklist, mode switching, `session/list` (741 sessions) and `session/load`
(7 turns replayed). Before that, 36/36 through our own wire harness against a real CLI.

The rest of v5.0 is **blocked on someone else**. IN-4 (webview as AHP client) needs "a host to talk
to", which is OUT-1 — posted to AHP #282 on 2026-08-15, unanswered a week later, and described in
our own issue index as the thing that "decides roadmap".

**So v5.0 as one release couples a finished half to a half nobody here can unblock.** This release
separates them along the line where the risk actually sits: everything we control ships; everything
Microsoft controls waits.

### The two gates

1. **v3.13.0 ships.** Lane A does not merge before it.
2. **OUT-1 is still unanswered at that point.** If Microsoft answers first and the AHP route opens,
   the calculus changes and this plan should be re-read rather than executed.

## 3. The work that is actually left

Everything above is done. This section is the release, and it is mostly packaging.

### 3.1 Packaging — the decision the release hinges on

**Today a VSIX ships nothing a user can point at.** `out/**` is in `.vscodeignore`, `esbuild.js`
never builds `src/acp/main.ts`, and `package.json` has no `bin`. The Zed run worked because it aimed
at a path inside a dev checkout.

**Bundling into the VSIX does not solve it.** VS Code installs to `publisher.name-<version>/`, so a
path a user writes into *their* editor's config breaks on *our* next release — silently, surfacing
as "agent exited" with no cause. Shipping a config that rots on our own cadence is worse than not
shipping.

**Recommended: a separate npm package with a `bin`.**

```
npx @darthmolen/copilot-cli-acp        # or a global install
```

Stable command, no version-pinned path, and it is the shape every other ACP agent already uses.

Open questions to settle before starting:

- **Does its version track the extension's or float?** Tracking is simpler to explain and means this
  release is genuinely "3.15.0" in both places. Floating is more honest if the two diverge later.
- **One repo or two?** Same repo is far less overhead and keeps `src/acp/` beside the manager it
  wraps. It needs an npm publish step that does not disturb `vsce publish`.
- **What does it depend on?** It needs the Copilot CLI. `CliBundleService` already solves this for
  the extension; the agent currently takes `--cli-path` or falls back to `resolveCliPath`. Decide
  whether the package declares `@github/copilot` as a dependency or resolves it the way the extension
  does.

**If this decision does not land, the release does not happen.** Better to say so than ship a
dev-only artifact with a version number on it.

### 3.2 Configuration ergonomics

A user currently needs absolute paths to `node` **and** the CLI, because a GUI-spawned process does
not inherit an nvm `PATH` — a failure that presents as a silent "agent exited". A `bin` removes most
of this. Finish it with `--print-config`, emitting a ready-to-paste block for the host:

```jsonc
// ~/.config/zed/settings.json
{ "agent_servers": { "Copilot CLI Chat": { "type": "custom", "command": "copilot-cli-acp" } } }
```

### 3.3 Polish that only matters once strangers use it

| Item | Why it matters outside our own sidebar |
| --- | --- |
| **stderr log level** | Zed labels all agent stderr `WARN`, so every `[DEBUG]` line reads as a warning in someone else's log. Default to a quieter level when serving ACP. |
| **Unlabelled session titles** | 740 threads imported into Zed; a good number titled `c0b8775b`, because `formatSessionLabel` falls back to the id prefix. Tolerable in our sidebar, a wall of hashes as thread titles elsewhere. Needs a product decision — first user message? date? — and it touches a function the sidebar shares. |
| **`close` / `fork` / `delete` unexercised by a real host** | Implemented and spike-verified; Zed never called them. Not a defect, but it is the untested corner. |

### 3.4 Documentation

A README section for external hosts: what the agent is, install, configure, what works, what does
not (`promptCapabilities` advertises no image/audio/embedded context). Plus the honest limitation
that **the agent brings its own model** — Copilot, via the CLI — and cannot be pointed at a local
LLM. That question came up within a minute of the first Zed launch and will come up again.

## 5. Verification

The gate that already exists, plus one that does not:

```bash
npm test                                                    # 2102 passing
node planning/spikes/acp-agent/spike-through-the-wire.mjs    # 36/36, real CLI
```

**New, and required before release:** the wire spike currently runs against `out/` in a dev checkout.
It must run against **the published artifact** — `npx @darthmolen/copilot-cli-acp` — or the release
is verified only in the one configuration no user will have. That is the same class of gap as
`out/**` being `.vscodeignore`d: everything passes, and none of it is what ships.

A second Zed run against the installed package, not the checkout, closes it.
