## Findings (evidence, not opinion)

**F1. ACP multiplexes sessions over one connection.** Every ACP request carries
`sessionId` — verified in the shipped schema (`@agentclientprotocol/sdk@1.3.0`):

| Request | Properties |
| --- | --- |
| `PromptRequest` | `sessionId`, `prompt`, `_meta` |
| `CancelNotification` | `sessionId`, `_meta` |
| `LoadSessionRequest` | `mcpServers`, `cwd`, `additionalDirectories`, `sessionId`, `_meta` |

So IN-3 **does** need an id→manager map. Your "two registries is a smell" instinct
was right to raise.

**F2. But the lifetimes differ, and your §3.3 is the proof.** *"A host must be able
to exist before its CLI session does."* A Lane B host can exist with
`sessionId === null`; a Lane A agent session cannot, because the agent **mints** the
id in `session/new`. There is no pre-id state to model agent-side. Your adoptable
null id is not incidental — it is precisely what makes yours a *presentation
binding* and mine a *protocol address*.

**F3. AHP deliberately does not specify agent process lifetime.** From the spec:
AHP *"stays agent-agnostic … without binding clients to a specific agent runtime."*
It says nothing about one-agent-per-session vs one-serving-many. **Do not plan
around a guarantee that is not offered.**

**F4. `CopilotClientProvider` survives v4.0 regardless.** Its value was never mainly
the sharing — it de-duplicated create-and-start and made the client lifecycle stop
being the session's business. Both hold at N=1. Worst case it manages one client
instead of several. It does not become a v3-only concern under any outcome.

**F5. ACP `cancel` is fire-and-forget.** A notification on the wire; an `AbortSignal`
on the agent side. It never awaits a reply.

**F6. CLAUDE.md:25 is stale — confirmed.** No test matching `size constraint`, or any
`main.js` size assertion, exists anywhere under `tests/`. Your open question 7.5 is
correct. Shared file, so Lane A did not touch it.

## Answers to §5

**Q1 — Does IN-3 grow its own session registry?**
Yes (F1), but it is not the same concept (F2). Keep both.
A sharper drift test than "same fields": watch for **presentation** concepts (which
surface, focus, tab state) appearing agent-side, or **runtime** concepts (model, tool
policy, CLI health) appearing host-side. Either means something is in the wrong
process.

**Q2 — Does the one-CLI-process invariant survive v4.0?**
The protocol will not tell you (F3). But ACP multiplexes (F1), so our agent process
naturally serves N sessions and the shared provider stays load-bearing inside it —
and the provider is justified even at N=1 (F4). **Keep designing around it.**

**Q3 — Does IN-4 assume extension-side routing survives?**
Your bet is right, with one refinement: the risk is **relocation, not scaffolding**.
Even if the webview speaks AHP directly, something must still map session → surface,
because the surfaces are ours. The registry may move (extension → webview) rather
than die. **§3.1's no-`vscode`/no-SDK constraint is what makes it portable — keep it
hard.**

**Q4 — Is §4's narrow-slice guard the right seam?**
Yes, strongly, and here is the vocabulary to match. IN-3's agent-facing surface is
ACP's session verbs:

| ACP method | Suggested slice on `ChatSessionHost` |
| --- | --- |
| `session/prompt` | `prompt(text): Promise<StopReason>` |
| `session/cancel` | `cancel(): void` — fire-and-forget, see F5 |
| `session/update` | an update stream |

Shape the public surface to those three and Task 5's 75 sites become
transport-agnostic **by construction** rather than by discipline.

## Recommendations

1. **`.manager` stays private.** Agreed without reservation. Cheap now, 75 call sites
   later.
2. **Model `cancel` as fire-and-forget**, not a request awaiting a reply (F5), or the
   shape will not survive the process boundary.
3. **Extract §2's unified reader as a reusable function** — this is the big one, see
   below.
4. **Naming:** Lane A will *not* call its map a "session registry." It will be named
   for routing protocol ids, so `ChatSessionRegistry` stays unambiguous under `grep`.
5. **Keep `ChatSessionRegistry` free of `vscode`/SDK imports** — that constraint is
   what protects the Q3 bet, not just test hygiene.
6. **Collision backstop (§3.5):** agree it must not throw inside `onSessionStarted`.
   Suggest it stays a warning but records *both* host handles in the log line, so the
   upstream bug is diagnosable rather than just noticed.

## The convergence neither side flagged

**Your §2 replay work lands directly on IN-3 scope item 2: `session/load`.**

`session/load` is ACP's history-replay method, and it needs exactly the reader you
are building — reconstructing tool state from `tool.execution_start` /
`tool.execution_complete`, with `success` giving status and `agentId` keeping
sub-agents separable.

**So: do not let Lane A grow a third reader.** If your unified reader lands as a
reusable function rather than inline in the switch path, IN-3's `session/load`
consumes it unchanged.

This argues for the "make them one reader" decision **independently of Task 7** —
there is now a third caller, in another process, that needs the same thing.
