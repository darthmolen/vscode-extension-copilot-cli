## 2. P2 was wrong in the direction that makes it cheaper

The reviewed plan said tool replay would need us to persist tool status ourselves, and that "faithful"
replay was impossible because the data does not exist on disk. **The data exists.** Measured on
session `af36eb01`, 469 events:

| Event | Count | Carries |
| --- | --- | --- |
| `tool.execution_start` | 48 | `toolCallId`, `toolName`, `arguments`, `model`, `turnId` |
| `tool.execution_complete` | 48 | `toolCallId`, **`success`**, `result.content` |

**26 of the 48 starts carry `agentId`**, so sub-agent tools stay separable on replay — the dock/transcript
split the live path makes is reproducible. Zero events were `ephemeral: true`.

So the defect is our **reader**: `SessionService.loadSessionHistory` parses `user.message` and
`assistant.message` and drops everything else. Fixing the reader removes the frozen-at-`running`
problem without adding any write path, because the status comes from `success` rather than from us.

**Also found, and not in the reviewed plan: two replay paths that disagree.** Session switch
(`extension.ts:1011`) reads JSONL and drops tools entirely; webview re-init (`getFullState()`) reads
in-memory state and produces the "Tool execution" wall. Same session, two histories. Task 7's
serializer must pick one, and either choice ships one of the two bugs — so they have to become one
reader.

**Implemented and shipped** in `56a7fe8` / `194afb5`; the plan and both review passes are archived at
`../completed/v3.13.0-p2-tool-replay.md`.

## 3. Task 4 — what was built and why it has these shapes

### 3.1 Both modules are free of `vscode` and SDK imports

Same constraint Task 1 adopted for `chatHtml.ts`, same reason: a module that imports `vscode` can only
be tested by patching `Module.prototype.require`, which is a documented cause of the suite's cross-file
flake. Everything host-shaped is injected. Checked and relied upon: **none of the five slash-command
services import `vscode`** — they already take their dependencies as parameters — so the host can own
them without pulling the extension host in.

### 3.2 Slash-command services are built per host, by an injected factory

This closes the Task 2 wart: `_setupRpcHandlers` constructed the services *during handler
registration* and assigned them back onto the context, so a second surface would rebuild and overwrite
them. `createServices(host)` is called once per host, lazily.

**Per host rather than per window, on evidence:** `InfoSlashHandlers` captures `getBackendState()` **at
construction**. Shared across sessions, one session's usage stats would report the other's. The
factory still lets the composition root share genuinely window-scoped collaborators (MCP registry, MCP
config service) by closing over them.

### 3.3 `sessionId` is `string | null` and adoptable

Forced by ordering: the id does not exist until `manager.start()` returns and `onSessionStarted` fires,
but the slash-command services are needed when handlers register, which can be earlier. **A host must
be able to exist before its CLI session does.** That is also Task 6 case (c) — "host starts fresh" —
so the mutability is load-bearing rather than convenience.

`adoptSessionId()` deliberately **keeps the transcript**: anything typed while the session was starting
belongs to the session that starts.

### 3.4 The registry holds hosts from birth, not from first id

This changed mid-session in response to one question — *what happens on a red path where the CLI
session never materialises but the host is there?* — and the answer exposed a hole.

Keyed by session id, a host whose CLI never started (auth failure, missing bundle, wrong Node —
`handleStartupError` returns with no id ever assigned) is **invisible**: `get()` misses it, `size` does
not count it, and `disposeAll()` on deactivate walks past it, stranding the subscriptions it will own
after Task 5. Worse, *Start New Session* re-enters the start flow, so a retry could build a second host
and orphan the first — violating "exactly one host" on precisely the path nobody thinks to check.

So: hosts live in a `Set` by identity; `hostsBySessionId` is a **secondary index** filled on adoption,
kept honest by an `onAdoptSessionId` hook the registry supplies. `disposeHost(host)` disposes by
identity, which is the only way to reach a host that has no id.

The lesson generalises: **identity was keyed on something that does not exist yet.**

### 3.5 Collision policy — decided provisionally, Task 6 should ratify

Two hosts claiming one session id: `reindex` logs a warning, the newcomer takes the index, and the
incumbent **stays live under its handle**. Silently disposing the incumbent would tear down a possibly
streaming session as a side effect of someone resuming a session already open. One-session-one-surface
says this situation is an upstream bug, not something to paper over, and Task 6 case (a) is what
prevents it — this is the backstop, not the mechanism. Open: should the backstop be louder? It should
**not** throw inside `onSessionStarted`.

### 3.6 One test passed without failing first, and is kept anyway

`runs its teardown once, however many times it is disposed` was green on arrival — clearing the
callback list already gave idempotence. Recorded rather than dressed up as a red-green cycle. It is
kept as a regression guard: it fails if `dispose()` stops clearing.

## 4. Proposed guard for Task 5 — `.manager` stays private

Task 5 reroutes **75 call sites** through the owning host. If those sites reach *through* the host
(`host.manager.sendMessage(...)`), Task 5 hard-codes 75 references to an `SDKSessionManager` that
v4.0 moves to the far side of a process boundary. If the host instead exposes a **narrow slice** —
send, abort, an event stream — the same sites are transport-agnostic and the manager can become an AHP
session handle without them noticing.

This is S4's `ManagedClient` lesson applied one layer up: declare the slice you touch, do not import
the concrete thing. **Recommendation: `.manager` is never public on `ChatSessionHost`.**

**Agreed by Lane A without reservation, and sharpened into a vocabulary.** Shape the host's public
surface to ACP's session verbs and Task 5's call sites become transport-agnostic *by construction*
rather than by discipline:

| ACP method | Slice on `ChatSessionHost` |
| --- | --- |
| `session/prompt` | `prompt(text): Promise<StopReason>` |
| `session/cancel` | `cancel(): void` — **fire-and-forget**, never awaiting a reply |
| `session/update` | an update stream |

`cancel` returning `void` is not a detail: on the wire it is a notification and an `AbortSignal`
agent-side, so a `Promise`-shaped cancel would not survive the process boundary.

### Addendum received 2026-08-17 — ACP's real vocabulary

Lane A cloned the ACP SDK **source** into `research/acp-sdk/` (v1.3.0) and corrected their own earlier
three-verb table, which had been read off the `.d.ts`. The agent-side session surface is eleven
methods: `new · load · list · delete · fork · resume · close · setMode · setConfigOption · prompt ·
cancel`. Full text: [`v3.13.0-lane-a-addendum-acp-vocabulary.md`](v3.13.0-lane-a-addendum-acp-vocabulary.md)
on `origin/feature/4.0-in3-acp-server`.

**What Lane B acts on:**

1. **`resume` and `load` are different methods — Task 6 must stop using one word for both.** Case (b)
   in Task 6's table ("stopped, resumable → host resumes") is really *two* operations: restart the CLI
   session (`resume`) **and** replay its history (`load`). P2's reader is `load`. Task 6 is written
   below with four verbs — **start / resume / load / attach** — for this reason.
2. **`dispose` over `close` is now a deliberate choice**, not an accident: the host is a VS Code
   object and `dispose()` is the idiom. Recorded because Q4 was asking whether the choice was made.
3. **Plan mode is a first-class ACP concept** (`session/set_mode`, `set_config_option`), not the
   bespoke flag we model. Not actionable in v3.13.0 — a note for Task 8 and v4.0.
4. **Fork does not converge.** ACP's `session/fork` has *no* message boundary; the Copilot SDK's
   `sessions.fork` takes `toEventId`. v3.14.0's per-message fork therefore stays an our-layer concept
   and must not be renamed toward the protocol.

**Process lesson, ours to copy:** their wrong table came from reading the `.d.ts` because the source
was not in `research/`, which made CLAUDE.md's SDK-First rule unfollowable for ACP. Anything Lane B
depends on whose source is not in `research/` deserves the same treatment before it is designed
against.

### The convergence neither side flagged

**§2's replay reader is IN-3 scope item 2, `session/load`.** ACP's history-replay method needs exactly
the reader described there — tool state rebuilt from `tool.execution_start` / `tool.execution_complete`,
`success` giving status, `agentId` keeping sub-agents separable.

So the reader must land as a **reusable function**, not inline in the session-switch path, or Lane A
grows a third one. This makes "unify the two readers" correct *independently of Task 7* — there is now
a third caller, in another process.

### The questions as originally put (kept for the audit trail)

Lane B is building a **client-side session registry**. Per the roadmap's layering,

```text
our extension (AHP client + VS Code integration) ──AHP──▶ host ──ACP──▶ our agent ──▶ Copilot SDK
```

Lane B sits at the far left, Lane A (IN-3) at the far right. Lane B's read is that the host is the
multiplexer, so nothing forwards a bundled stream through us to fan out: IN-3 receives N independent
`session/new` calls, and the extension subscribes per session. **Questions, in priority order:**

1. **Does IN-3 grow its own session registry?** An ACP server handling N concurrent sessions needs
   per-session multiplexing. Two session registries in one product is a smell, even across a declared
   seam. Are they the same concept in two processes, or genuinely different lifetimes? If they start
   growing the same fields, one of them is in the wrong place.
2. **Does the one-CLI-process invariant survive v4.0?** v3.13.0 designs around *both sessions live, one
   shared `CopilotClient`* via S4's provider. If the Agent Host owns agent process lifetime, that stops
   being ours to insist on — and `CopilotClientProvider` becomes a v3-only concern rather than an
   invariant worth planning around.
3. **Does IN-4 assume extension-side routing survives?** Lane B is betting that "session id → which
   surface shows it" outlives the transport, because the *surfaces* are ours (sidebar, tabs, dock) and
   only the pipe changes. If IN-4's design has the webview speaking AHP directly, that bet is wrong and
   `ChatSessionRegistry` is scaffolding.
4. **Is §4's narrow-slice guard the right seam?** If IN-3 already defines the agent-facing session
   interface, Lane B should shape the host's public surface to match it rather than invent a parallel
   vocabulary.

Standing caveats acknowledged: OUT-1 is awaiting a reply, AHP is draft with promised breaking changes,
and vscode#325827 is untriaged with no `agentHost` proposal file. The hybrid posture — build only what
survives every outcome — is the reason §4 exists.
