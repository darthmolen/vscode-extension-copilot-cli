## Context

The extension had one chat surface — the sidebar `WebviewView` — driven by one module-level
`sessionManager`, one `BackendState` singleton, and one `ExtensionRpcRouter`. The pattern this exists
to enable is a long task running in the sidebar while a second conversation happens in an editor tab.
That needs a session to be viewable in a tab or the sidebar interchangeably, so "a chat surface" has
to become a thing you can have more than one of.

Slice 2a (`CopilotClientProvider`) was reassigned to Lane A and landed as spine step **S4** (`ae1c597`,
PR #42, already on `main`). Both lanes have rebased; the sync point is satisfied.

### Decisions taken

| Question | Decision |
| --- | --- |
| Concurrency | Both sessions live, **one shared `CopilotClient`** (one CLI process), via S4's provider |
| Session ↔ surface | **One session, one live surface.** Never mirrored |
| New Tab | Opens a **new** session, not the current one — active file seeded |
| `/btw <question>` | New session in a tab, pre-seeded — New Tab + send. Does **not** inherit history |
| Fork | Opens the fork in a tab; sidebar stays on the parent |
| Concurrent writes | **Detect and label, don't lock** — see P1 |

One-session-one-surface is load-bearing. It dissolves move-vs-mirror: no scroll divergence, no double
streaming, no second router per session, no shared-transcript reconciliation.

## What Tasks 1–3 actually built

Read these before Task 4; two of them constrain it.

**Task 1 — `src/extension/webview/chatHtml.ts` + `chatHtmlAssets.ts`.** The document builder is
deliberately **pure** (takes resolved strings, not a `vscode.Webview`), because importing `vscode`
would make it unrequirable from a plain mocha process — so the CSP and nonce could only be tested by
patching `Module.prototype.require`, a documented cause of the suite's cross-file flake. The vscode
URI resolution lives in the sibling file. `ChatPanelService` (Task 7) uses both.

**Task 2 — `src/extension/rpc/registerChatHandlers.ts`.** 33 handler registrations, moved out of
`ChatViewProvider._setupRpcHandlers`, taking an explicit 27-member `ChatHandlerContext`.
`ChatViewProvider._handlerContext()` adapts the view to it.

> ⚠️ **Two constraints for Task 4.** The context uses **getters**, not copied values — several members
> are assigned after construction and handlers run long after registration, so snapshotting would
> freeze resolve-time values. Five members (`infoHandlers`, `codeReviewHandlers`,
> `notSupportedHandlers`, `mcpConfigService`, `cliPassthroughService`) are *assigned by the handler
> module* and so need **setters** too — accessor-only properties throw under strict mode.
>
> That they are assigned at all is a wart inherited from `_setupRpcHandlers`: it constructs the
> slash-command services *during* handler registration. Harmless with one surface. **A second surface
> would rebuild and overwrite them.** Task 4 should move this construction to `ChatSessionHost`.

**Task 3 — `src/backendState.ts` split.** `SessionState` (per conversation) and
`WorkspaceRuntimeState` (per window: workspace path, active file, MCP tools/statuses).
`BackendState` remains a **facade** delegating to both, so all 16 existing call sites still work
untouched — that is what made Task 3 landable alone. `getWorkspaceRuntimeState()` returns the shared
instance the facade uses.

## Prerequisites

P2 is a hard blocker for Task 7. P1 was raised as a blocker by review and is **downgraded on
evidence**; its home is still settled at Task 4.

### P1 — Concurrency contract (downgraded, not dropped)

**The original premise was wrong and is corrected here**, because it is recorded incorrectly in two
reviewed documents. An earlier draft claimed that accepting one session's diff writes a
snapshot-derived result and discards the other session's edits. **That describes no code that
exists.** The only consumer of `snapshot.tempFilePath` is `sdkSessionManager.ts:1239`, which passes it
as `beforeUri` to the diff view; `cleanupSnapshot` follows at :1253. Nothing writes it back — there is
no restore or revert path, and `chatViewProvider.ts`'s accept/reject handlers are
`onAcceptPlan`/`onRejectPlan`, i.e. plan mode, not file diffs. **Snapshots are display-only; the CLI
writes files.**

`FileSnapshotService` is still per-manager (`sdkSessionManager.ts:465`), so what remains is:

- **Misattributed diffs (ours, cosmetic).** If session B edits a file between A's snapshot and A's
  diff render, A's diff shows B's changes as A's.
- **Two CLI agents racing on one file (not ours).** Both run `onPermissionRequest: approveAll` and the
  CLI performs the writes. We cannot compare-and-swap what we do not write. Out of scope.

**Decision: detect and label.** An `EditActivityLog` (`Map<path, { sessionId, at }>`) on
`WorkspaceRuntimeState` — recorded at snapshot capture, cleared at cleanup. When a diff renders and
another session touched that path in the window, label it *"also modified by `<other session>`"*.
Nothing blocked, no new RPC on the write path.

### P2 — Tool messages corrupt any replayed transcript (**blocks Task 7**)

`chatViewProvider.ts:687-696` persists every tool call to state as an assistant message with content
`description || name || 'Tool execution'`, `type: 'tool'`, `status: 'running'`. On replay,
`main.js:605-614` rebuilds each entry as `{role, content, timestamp}` — dropping `type`, `toolName`,
`status`. Every tool call returns as a plain bubble reading "Tool execution", frozen at running.
Observed live: `[Init] Sending 61 messages to webview` producing a wall of identical bubbles.

**Root cause: the two `Message` interfaces are not assignable to each other.**

| | `backendState.ts` `Message` | `shared/models.ts` `Message` (the wire contract) |
| --- | --- | --- |
| `role` | `'user' \| 'assistant' \| 'system'` | `'user' \| 'assistant' \| 'reasoning' \| 'tool'` |
| `type` | **required**, includes `'tool' \| 'error'` | optional, **no `'tool'`, no `'error'`** |
| `toolName`, `status` | present | **absent** |

The wire type cannot express a tool message, so `main.js:609` does `const role = msg.type || msg.role`
— promoting `type` into `role` and discarding the rest. **Three change sites, all required:**

1. `src/shared/models.ts` — widen `Message.type` to include `'tool' | 'error'`, add `toolName?` and
   `status?`, and reconcile the two `role` unions. **Open decision: what the merged union is.**
2. The serialise path — `getFullState()` → `sendInit` must carry the full shape.
3. `src/webview/main.js:605-614` — stop collapsing `type` into `role`; forward all three fields.

This is the same replay path `registerWebviewPanelSerializer` uses to restore a tab, so tab restore
inherits it wholesale. Fix the round-trip, not the symptom.

**4. `ChatSessionHost` + `ChatSessionRegistry`, one host only.** New `src/extension/session/`.
The host owns per session: `sessionId`, its `SDKSessionManager`, its `SessionState`, and the event

```ts
interface ChatSessionRegistry {
    get(sessionId: string): ChatSessionHost | undefined;
    getOrCreate(sessionId: string): Promise<ChatSessionHost>;  // Task 7 / serializer entry point
    dispose(sessionId: string): void;
    disposeAll(): void;
}
```

`getBackendState()` has **16 call sites** — measured: `chatViewProvider.ts` ×12, `extension.ts` ×4,
`hostBridge.ts` ×0 (S3 already relocated `getActiveAgent` — do not go looking there), plus the
definition. *Verify:* exactly one host exists; suite green.

**5. Reroute `chatProvider.*` through the owning host.** **75 call sites across 39 methods** in

This is the largest workstream here — roughly 3.5× the `getBackendState()` migration, and multi-session

*Verify:* drop `chatProvider` from the enclosing scope of `registerChatProviderHandlers` and

**6. Separate surface attachment from session bootstrap.** Today the ready flow is split across
`chatViewProvider.ts` and `extension.ts` and includes auto-resume on webview readiness. Copied into
tabs, that re-resumes or double-inits a live session. Rule: **the host owns resume/start; surfaces
only attach and detach.**

| Case | Host action | Surface shows |
| --- | --- | --- |
| (a) session live | `registry.get()` hits — **attach only, start nothing** | replayed transcript, streaming continues |
| (b) stopped, resumable | `getOrCreate()` → host resumes | replayed transcript, then live |
| (c) missing / expired | `getOrCreate()` → host starts fresh | empty state + notice |

*Verify:* assert no `createSession`/`resumeSession` fires on the (a) path.

## Entry points (Task 8)

Three verbs, each one mechanism. Keeping them distinct is what makes this teachable:

| Verb | Result |
| --- | --- |
| **New Tab** | Empty **new** session in a tab, active file seeded |
| **`/btw <question>`** | New session in a tab, pre-seeded — New Tab + send |
| **Fork / Fork from here** | A **copy** of the current session in a tab |

`/btw` deliberately does not inherit history — that is what fork is for. So once New Tab exists, `/btw`
is New Tab plus one `sendMessage`.

### Placement

- **`editor/title`** — `$(split-horizontal)`, tooltip *Copilot CLI: New Tab*. **Do not use
  `when: editorFocus`.** The existing `openChat` icon uses it and is therefore invisible whenever focus
  sits in the chat webview — which is most of the time you would reach for it. It reads as the icon
  randomly not existing. Use `editorIsOpen`, or no `when` at all.
- **`view/title` on `copilot-cli.chatView`** — **repurpose, don't add.** The existing `newSession`
  `$(add)` duplicates the webview's own `+` beside the session dropdown. Make the toolbar one *New Tab*
  and leave the in-panel `+` as new-session-in-sidebar.
- **`refreshPanel`** — drop from `view/title` (palette-only). It exists to paper over P2 and triggers it.
- **Per-tab actions** — `when: activeWebviewPanelId == 'copilotChatPanel'` for things the sidebar
  cannot have (⑂ Fork This Session, ↩ Move Back to Sidebar).
- Active file seeding honours `copilotCLI.includeActiveFile`; it does not force it.
