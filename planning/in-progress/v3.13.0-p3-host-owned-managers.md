  caught only because the test came first — including one where a fake was lying, and one where a
  scripted edit silently no-op'd.
- **The suite is flaky; a failure counts only if it also fails alone** (`npx mocha <file> --timeout
  20000`). The victim rotates. There is **no** sanctioned baseline failure. Equally: **one green run
  is not evidence** — verify anything you are shipping over three.
- **Never source-scan in tests.** Ten such tests were deleted during Task 7 and 44 more assertions in
  T0, each because a correct refactor stopped a string matching. Assert behaviour by running it.
  Backlog: `../backlog/source-scan-tests.md`.
- **Verify claims against the codebase, including your own.** Two review points this cycle were
  factually wrong and were rejected on evidence; two others were right about code I had written.
- **Live-verify every task.** Build with `./test-extension.sh`, reload the window, save the Output
  Channel to `tests/logs/server/3-13-0-<what>.log`. Two of this cycle's worst defects were invisible
  to 2,043 unit tests and obvious in a log within minutes, because both needed two surfaces starting
  at once and only a reload does that.
- **The recurring failure is one truth living in two places, kept in step by memory.** Three
  hand-built init payloads, two identically-wrong argument formatters, a start decision computed
  twice. When you find yourself writing the second one, collapse instead — or bind them with a test
  that compares values.

### Invariants not to break

- **One session, one live surface, never mirrored.** `attachSurface` replaces for this reason.

- **`.manager` is a true `#private` field** on `ChatSessionHost`. 75 call sites were rerouted through

- **Lane B does not edit `sdkSessionManager.ts` or `hostBridge.ts`** — Lane A owns both. A change

## 1. Why now

Task 7 shipped a second surface. The module-level `sessionManager` in `extension.ts` was *"the
window's session"* while there was one surface; it is now **"whichever session started last"**, and
three live defects have already come out of that:

| Found | Symptom | Status |
| --- | --- | --- |
| §7.4 | New Tab mirrored the sidebar — one session, two surfaces | fixed, by removing a second decision site |
| §7.7 | Two concurrent starts clobbered the shared handle; both hosts adopted one id, one CLI session orphaned | fixed by returning the manager instead of reading the slot |
| §7.7 | **The tab's dropdown and New Session drive the sidebar** | **not fixed — this task** |

The first two were patched at the seams. The third cannot be, because the seam *is* the global.

## 2. What the global provides today: nothing window-scoped

Every read, classified. There is exactly one bucket.

| Reads | What they actually want |
| --- | --- |
| `enablePlanMode`, `disablePlanMode`, `acceptPlan`, `rejectPlan`, `getPlanFilePath` | the session the user is looking at |
| `listMcpServers`, `listConfiguredMcpServers`, `getAvailableModels`, `validateAttachments` | the session the surface belongs to |
| `stop()` in new-session / switch-session / stop-chat, the fork handler | that session |
| the `isRunning()` guards | *"is mine running"* — the question C2 proved it cannot answer |
| `dispose()` in `deactivate` | **all** of them, which it does not do |

Not one is *"a thing this window has, once"*. `deactivate` looks window-scoped and is the opposite:
it disposes a single manager, so every other host's leaks — already true on session switch, one worse
per tab.

**The genuinely window-scoped thing already has a home and is wired wrong.**
`CopilotClientProvider` owns the CLI process. Its own header says it *"lets N `SDKSessionManager`s
share one CLI process"*, and `SDKSessionManager` carries `ownsClientProvider` guarding `stop()`. The
seam is complete — and the single construction site passes six arguments where the provider is the
seventh. **It has never been shared.** Every manager spawns its own CLI.

## 3. Target shape

```
window   CopilotClientProvider     one CLI process       [today: N, never shared]
         ModelCapabilitiesService  one model catalogue   [today: one per manager]
  host   SDKSessionManager         one session, owned and disposed by its host
           workSession  live  →  the host's surface
           planSession  live  →  no host, no surface  (unchanged; see §9)
```

The module-level `sessionManager` is deleted. Not deprecated — deleted, so "reads the wrong session"
stops being expressible.

## 4. Design

### 4.1 The host's command surface grows to cover what the global answered

`ChatSessionHost` already exposes `prompt · cancel · switchModel · compact · rename · selectAgent ·
reloadAgents`, all routed through the `#private` manager. The additions are the same shape:

```ts
enablePlanMode(): Promise<void>
disablePlanMode(): Promise<void>
acceptPlan(): Promise<void>
rejectPlan(): Promise<void>
stop(): Promise<void>
planFilePath(): string | null
availableModels(): Promise<any[]>
validateAttachments(paths: string[]): Promise<{ valid: boolean; error?: string }>
listMcpServers(): Promise<any[]>
listConfiguredMcpServers(): Promise<Record<string, any>>
```

`any[]` rather than `ModelInfo[]` / `McpServer[]` on purpose, matching how `SessionManagerLike`
already declares `compactSession(): Promise<any>`. `ChatSessionHost` is free of `vscode` and SDK
imports so it stays requirable from plain mocha and portable to v4.0; importing SDK types for these
signatures would spend that for decoration.

`.manager` stays `#private`. Task 5 rerouted 75 call sites specifically so v4.0 can swap the manager
for an AHP session handle; these ten must not be the exception that undoes it.

Each states its own not-live behaviour rather than relying on the caller to guard. `acceptPlan` in
particular currently returns silently when `currentMode !== 'plan'`, which is how the wrong-session
bug hid; it should say something.

### 4.2 Signals carry their surface — there is nothing to resolve

The first draft of this spec proposed a `commandTarget()` resolver with a sidebar fallback. **That
was wrong, and the trace shows why.** Walking `/plan` typed in tab1:

| # | Layer | Identity |
| --- | --- | --- |
| 1–3 | input → `CommandParser` → `main.js` → `rpc.togglePlanMode()` | implicit — this webview |
| 4 | `WebviewRpcClient._send` → `postMessage` | **the channel is the identity** |
| 5 | `ExtensionRpcRouter` — **one per surface**, built with tab1's webview | explicit, unambiguous |
| 6 | `registerChatHandlers`, closure over `ctx.sessionHost` | **explicit — the host is right there** |
| 7 | `vscode.commands.executeCommand('…togglePlanMode')` | **destroyed, on this line** |
| 8 | `handleTogglePlanMode` → the module global | gone |

And the return trip (`onDidChangeStatus` → `ChatSessionHost.applyStatus` → `this.surface`) **never
loses identity**, because Task 5 fixed it. Events flow out correctly; signals flow in blind. That
asymmetry is the whole of defect C.

A resolver exists to recover identity that is absent. Here identity is present at layer 6 and
discarded at layer 7, so a resolver would be machinery to reconstruct what we chose to throw away one
line earlier. The fix is to stop throwing it away:

```ts
ctx.reg(ctx.rpcRouter.onAcceptPlan(async () => {
    await ctx.sessionHost?.acceptPlan();
}));
```

Five handlers, five deletions of `executeCommand`: `onSwitchSession`, `onNewSession`,
`onTogglePlanMode`, `onAcceptPlan`, `onRejectPlan` (`registerChatHandlers.ts:154, 159, 174, 183,
188`).

**The palette is the only surface-less origin, and it gets a `when` clause, not a guess.** A context
key set while a chat surface has focus gates the palette entries; the commands take the focused
surface's host. Invoked without one — an odd keybinding, a programmatic call — they **no-op with a
message**. Never pick a surface the user did not indicate. Where only the sidebar exists it is not a
fallback but the sole candidate, and the `when` clause makes that case unambiguous rather than lucky.

### 4.3 Manager lifetime moves to the host

- `ChatSessionHost.dispose()` disposes its manager. `detachManager()` keeps its meaning (drop the
  subscriptions, keep the manager) so a session switch still works.
- `ChatSessionRegistry.disposeAll()` therefore reaches every manager, and `deactivate` stops calling
  `sessionManager.dispose()` on one.
- **`wireManagerEvents` stops pushing into `context.subscriptions`.** It registers roughly ten
  window-scoped handlers per manager into extension-lifetime storage, so today every session switch
  leaks a set and every tab adds one. They belong to the host that owns the manager.

### 4.4 A closed tab winds its session down — when the work is finished

Today, closing a chat tab disposes the *surface* and detaches it, but leaves the host and its manager
alive for the life of the window. Open and close tabs over a day and that is a live CLI session each,
with no UI. Killing the session on close is the other extreme: it would abort a task the user set
running and merely stopped watching.

**The rule: an orphaned host is a host with no surface, on a countdown that any reattach cancels.**

| Host state | Behaviour |
| --- | --- |
| has a surface | normal |
| no surface, work in flight | wind down at the next idle |
| no surface, idle | wind down now |
| reattached before winding down | countdown cancelled |

The mechanic exists and is unused. `session.idle` already arrives at `sdkSessionManager.ts:936` and
is only logged; its contract is *"the session is idle with no background agents or attached shell
commands in flight"*. `_isInTurn` is already tracked from `assistant.turn_start`.

Two things to get right:

- **Idle is a transition, not a state.** It is `ephemeral: true`, never written to the event log, and
  fires at the end of *every* turn. So the rule is "the first idle after the surface went away", and
  it must be re-armed rather than assumed. If the host is not in a turn when the surface goes, there
  may be no further idle at all — wind down immediately instead of waiting for one.
- **The host cannot dispose itself cleanly**, because the registry holds it in two collections.
  `releaseWhenIdle()` therefore signals through an injected `onReleased` callback the registry
  supplies, the same shape as `onAdoptSessionId`, which calls `disposeHost`.

`ChatPanelService`'s panel-dispose handler calls `host.releaseWhenIdle()` explicitly rather than
`detachSurface` implying it. The sidebar never calls it: `closingEndsSurface` already distinguishes
"VS Code hid the view and will re-resolve it" from "the user closed the tab".

`SessionManagerLike` gains `onDidBecomeIdle(handler)` and a busy predicate. No new reach through
`.manager`.

> **A hung turn never goes idle, so its host never winds down.** That is exactly today's behaviour
> for every host, so it is not a regression, and a timeout is not proposed — a wall-clock deadline
> that kills a long legitimate task is worse than a session that outlives its tab.

### 4.5 Reconnecting to a session that is still running

Half of this exists. `ChatPanelService.openSession` already consults `registry.get(sessionId)`,
reveals the surface already showing it, and otherwise attaches to the existing host —
`ensureStarted()` returns immediately when `isLive`. Opening a **tab** for a live session already
reattaches rather than restarting.

**`handleSwitchSession` does none of it**, and that is the dangerous half. It stops the *global*
manager — since Task 7, possibly another surface's — then `startCLISession(context, true, sessionId)`
builds a **second** `SDKSessionManager` resuming the same id. Two managers, one session directory.

So the dropdown adopts the same rule the panel service already follows:

1. `registry.get(sessionId)` has a host **with** a surface → **reveal that surface.** Decided: reveal,
   never steal. Stealing would blank a surface out from under whoever is looking at it, and
   one-session-one-surface is the invariant the whole task rests on.
2. Host **without** a surface (its tab was closed, wind-down pending) → attach this surface to it and
   **cancel the wind-down**. This is the reconnect the closed-tab flow needs.
3. No host → resume from disk, as today.

**And the SDK already tells us when we get this wrong.** `StartData.alreadyInUse` and
`ResumeData.alreadyInUse` — *"Whether the session was already in use by another client at start /
resume time"* — appear in every `session.start` event we log, and our source references them **zero
times**. Free, authoritative, and currently discarded. Wiring it as a loud warning is the backstop
behind the registry check, the same way the two-hosts-claim warning sits behind `registry.get()`.

VS Code will not resurrect a closed webview panel, so there is no automatic route back to a closed
tab. Manual reselection from the dropdown is the route, and the above is what makes it reconnect
instead of double-start.

### 4.6 A session remembers its model — folded in from the backlog

`planning/backlog/session-model-persistence.md`, decided 2026-08-21 to ride along rather than be
revisited later. It names `handleSwitchSession` and `onSessionStarted` as its touch points and **P3
step 2 rewrites both**, so doing it separately means opening the same functions twice. It is also
row one of CLAUDE.md's *"intentional actions are treated intentionally"* table, still unresolved:
switching model mid-session is a gesture, `copilotCLI.model` is a standing default, and today the
default silently wins back on the next resume.

**Storage: `session-model.txt`, beside `session-name.txt`.** Plain text, one value, single purpose —
matching the precedent already in that directory, and with no read-modify-write to race. Deliberately
*not* merged with P4's `session-pairing.json`: the pairing is written once at plan-session creation
and never edited, the model is rewritten on every switch, and coupling two different lifetimes into
one file buys nothing but a lost-update window.

**Write** — on `model_switched`, in `wireManagerEvents`, which now has the owning host. Disk I/O for
`~/.copilot/session-state` belongs to `SessionService`, which already owns `writeSessionName`; it
gains `writeSessionModel` / `readSessionModel`. `ChatSessionHost.applyStatus` keeps doing what it does
(record on its own state, tell its own surface) and gains no filesystem dependency.

**Read — and the ordering is the part to get right.** The persisted model must reach the *manager*,
not only the state, or the CLI starts on the config model while the UI displays the persisted one.
So the read happens **before** `new SDKSessionManager(...)` in `startCLISession` and feeds
`config.model`; `recordSessionStart` then receives the same value it already receives, and stays
pure. Precedence: persisted → `copilotCLI.model` → `DEFAULT_MODEL`. The config default therefore
applies to **new sessions only**, which is what the backlog asks for.

Not in scope: `copilotCLI.planModel`. A plan session already picks `planModel || model`, and whether
a plan session persists its own choice is a question for P4, where the work↔plan relationship exists
to answer it.

### 4.7 One CLI process

Build one `CopilotClientProvider` at the composition root and pass it as the seventh argument. Two
things move with it, both genuinely window-scoped:

- **`ModelCapabilitiesService`** is the provider's `onClientStarted` hook and is a *model catalogue* —
  available models do not differ per session. One instance, injected.
- **Stopping it.** With an injected provider `ownsClientProvider` is false everywhere, so nobody stops
  the CLI. `deactivate` must, after the registry has disposed its hosts.

`useYolo` and `workingDirectory` already read window-wide config and the workspace folder.

### 4.8 What stays window-scoped

`WorkspaceRuntimeState` (already), the status bar, `SubagentPanelService`, the MCP registry and
config service, `CliBundleService` / `CliCapabilityService`, and the two above. Everything else is a
session's.

## 5. Spikes required before the code depends on them

Per CLAUDE.md's SDK-first rule, both are cheap scripts in `planning/spikes/`, run against a real CLI,
before the extension is written against the assumption.

**S-A `planning/spikes/shared-client/` — one provider, two managers.** The sharing path has never
executed. Prove two managers over one `CopilotClientProvider` run two live sessions, and that
stopping one does not stop the other's CLI. If it fails, §4.6 drops out and everything else still
lands; N processes is a cost, not a correctness problem.

**S-B `planning/spikes/session-already-in-use/` — two clients, one session id.** Resume the same
session from two managers and record what actually happens: what `alreadyInUse` reports on each, and
whether `events.jsonl` interleaves coherently or corrupts. This governs how hard the §4.5 guard has
to be — a warning if the runtime copes, a hard refusal if it does not. **Do not infer this from the
field's existence.** That it is reported rather than rejected suggests tolerance; it does not
establish it.

## 7. Testing

The seams are already `vscode`-free, so most of this is plain mocha:

- **Host verbs** — each forwards to its own manager and no other; each is a no-op with a clear message
  when the host is not live. Two hosts, one command, assert the other did not move.
- **The five handlers** — a signal from surface A reaches host A's manager and never host B's. This
  is defect C, as a test.
- **`handleNewSession` / `handleSwitchSession`** — the *target* host restarts; a bystander does not.
- **Reveal-or-reattach** — live session with a surface → revealed, no second manager; live session
  without one → attached, wind-down cancelled, nothing started; no host → resumed from disk.
- **Wind-down** — orphaned mid-turn disposes on the next idle, not before; orphaned while idle
  disposes at once; a reattach between the two cancels it; a second idle after disposal is harmless.
- **Lifetime** — `disposeAll()` reaches a host that never got a session id; `wireManagerEvents`
  subscriptions die with their host.
- **Model persistence** — a switch writes the session's file; a resume reads it in preference to the
  config default; a *new* session takes the config default; a missing or unreadable file falls back
  without throwing. Two sessions, two models, neither reading the other's.
- **New session starts blank** — `host.state` has no messages after a new session, so a subsequent
  `sendInit()` cannot render the previous conversation.

**Live**, and these matter most because every defect so far surfaced here and not in the suite: the
tab's dropdown switches the *tab*; New Session in the tab makes a new session *in the tab*; plan mode
entered and accepted in the sidebar while a tab is open; close a busy tab and watch it wind down at
idle; reselect a closed tab's session and confirm one manager, not two; `ps` for copilot node
processes before and after §4.6.

## 8. Risks

- **Plan mode is the sharpest edge.** `acceptPlan` no-ops silently off plan mode, which is how the
  wrong-session bug hid. Routing fixes the routing; the silent return should become visible.
- **`handleForkSession`** takes the manager directly (`const manager = sessionManager`). It needs the
  host, and fork is Task 10's subject — keep the change mechanical here.
- **Deleting the global is a wide diff** — 34 lines, most one-for-one. The risk is a missed
  `!sessionManager` guard becoming an unguarded host call, which is why every new host verb states
  its own not-live behaviour.
- **Wind-down changes when sessions end**, which users will feel. It is the one behavioural change in
  a task that is otherwise a re-plumbing, and it wants its own live pass.
- **Both spikes are unproven paths** and are gated accordingly.

## 9. Standing decisions, carried forward

Settled earlier in v3.13.0 and still binding. Disagree with the reasoning, not by accident.

| Question | Decision |
| --- | --- |
| Concurrency | Both sessions live, **one shared `CopilotClient`** (one CLI process) — §4.7, still unproven |
| Session ↔ surface | **One session, one live surface.** Never mirrored |
| New Tab | Opens a **new** session, not the current one — active file seeded |
| `/btw <question>` | New session in a tab, pre-seeded — New Tab + send. Does **not** inherit history |
| Fork | Opens the fork in a tab; sidebar stays on the parent |
| Switching to a session another surface shows | **Reveal that surface. Never steal** (§4.5) |
| Restoring a tab | **No freshness gate** — always restore (§4.5 / checkpoint §7.5) |
| Concurrent writes to one file | **Detect and label, don't lock** — P1, downgraded not dropped |

**Ownership and rendering are different questions, and our invariant constrains only the first.**
Reading `anthropic.claude-code-2.1.235`'s bundle showed one conversation drawn in an editor tab *and*
the secondary sidebar at once: their `broadcastSessionStates()` sends every session's state plus
`activeSessionId` to every surface, tabs are **pinned** via a `sessionPanels` map and the sidebar is a
**follower**. That is one owner and two viewports, not two owners. We stay one-owner — recorded so
reveal-not-steal is visibly a choice rather than the only option anyone thought of. Their
`createPanel` also opens with `sessionPanels.get(id)` → `reveal()`, which is the collision rule we
arrived at independently.

## 10. P4 — work↔plan pairing (designed, spec not written)

Approved in conversation 2026-08-21. Write the spec after P3 lands, because it hangs state off hosts
this task moves.

**Why:** 189 of 1,282 sessions on disk are `-plan` sessions, and **164 of the 428 in this workspace's
dropdown** — 38% of the list is half a conversation that only makes sense beside its parent. The
`-plan` suffix is known to exactly one file (`sdkSessionManager.ts`), so nothing else can tell a plan
session from a work session.

**Approach 1, plus a host pointer:**

- A `session-pairing.json` written **on the plan session**, pointing at its work session. Child→parent,
  one writer, written once — a second plan later is a new child record, never an edit to the parent.
- **One resolver** (`src/extension/session/sessionPairing.ts`, `vscode`-free) exposing
  `roleOf` / `workIdFor` / `planIdsFor`. The record wins when present; the `<id>-plan` suffix is a
  read-only fallback that **rides indefinitely** — a reconciliation resolver, tested in code, not two
  writers kept in step by memory.
- **Dropdown: adjacent and marked.** Pairs sorted together, group ordered by the newest mtime in the
  group, child labelled `↳ Plan: <parent name>`. The child's label must name its parent — a native
  `<select>` shows only the selected option when collapsed, so `↳ Plan` alone reads as nothing.
  Orphans (parent deleted) become their own top-level group; nothing becomes unreachable.
- **`host.pairing`**, with the 📋 View Plan button as its day-one caller — it currently reads
  `sessionManager?.getPlanFilePath()`, one of the 34. A bare `role` field was rejected as dead: no host
  is ever a plan session today.

**Checked and rejected:** the SDK offers nothing to hang this on. `SessionConfigBase` has ~40 fields
and no metadata slot. It *does* have `isDetached` ("hidden from normal resume lists", with
`includeDetached` defaulting false on `sessions.list`) and `detachedFromSpawningParentSessionId` — a
precedent for the shape, but neither is settable by us.

**Out of scope for P4:** liveness. No cross-session reads, questions or guards. The near-term payoff is
the dropdown; the north star is *"what was the plan, what is the plan"*, and the record is what makes
any of it possible later.

> **Not in the SDK but worth knowing:** `SessionConfig` has `onExitPlanModeRequest`. The SDK has a
> *native* plan-mode concept. It does not change P4, but it is a live question for whether our
> dual-session plan mode survives v4.0.

### Task 8 — entry points + toolbar cleanup

Three verbs, one mechanism each. Keeping them distinct is what makes them teachable:

| Verb | Result |
| --- | --- |
| **New Tab** | Empty **new** session in a tab, active file seeded |
| **`/btw <question>`** | New session in a tab, pre-seeded — New Tab + send |
| **Fork / Fork from here** | A **copy** of the current session in a tab |

`/btw` deliberately does not inherit history — that is what fork is for. Once New Tab exists, `/btw`
is New Tab plus one `sendMessage`.

Placement:

- **`editor/title`** — `$(split-horizontal)`, *Copilot CLI: New Tab*. **Drop `when: editorFocus`.**
  The existing `openChat` icon uses it and is therefore invisible whenever focus sits in the chat —
  which is most of the time you would reach for it. Use `editorIsOpen`, or no `when` at all.
- **`view/title` on `copilot-cli.chatView`** — **repurpose, don't add.** The existing `newSession`
  `$(add)` duplicates the webview's own `+`. Make the toolbar one *New Tab*.
- **`refreshPanel`** — drop from `view/title`, palette-only. *(Re-argue first: its stated reason —
  that it triggers the replay corruption — was fixed by P2.)*
- **Per-tab actions** — `when: activeWebviewPanelId == 'copilotChatPanel'` for things the sidebar
  cannot have (⑂ Fork This Session, ↩ Move Back to Sidebar).
- Active file seeding **honours** `copilotCLI.includeActiveFile`; the New Tab click seeds *that file*
  regardless, and does not rewrite the setting.

step 2 takes. That backlog was rechecked 2026-08-21 and two of its four claims have moved; read the
corrections inline there before actioning it.

### Task 9 — a deliberate session choice is recorded

`determineSessionToResume` asks `SessionService.getMostRecentSession` — **mtime only**. Switch to an
older session, read it without sending anything, reload, and you are back on the newer one, because
your choice was never written down. CLAUDE.md's *intentional actions* principle applied to session
selection.

**After Task 8, because that is when it hurts.** With one surface it is a single wrong transcript;
with N tabs reachable, every surface restores from the same ambient heuristic.

- **Tabs already have their answer** — the serializer persists each panel's sessionId.
- **The sidebar has none.** Record its session in `context.workspaceState` on switch or start, and
  prefer that over mtime.
- **Scope it.** Recording *which* session does not override `copilotCLI.resumeLastSession`, which says
  *whether* to resume and stays the user's to set.

*Verify:* switch to an older session, send nothing, reload — that session comes back. With a tab open
on a second session, both surfaces restore their own.
