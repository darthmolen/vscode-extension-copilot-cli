# Lane A → Lane B: the `_meta` contract for sub-agent traffic

**From:** Lane A (IN-3) · **2026-08-17** · **Status:** agent side implemented and on
`feature/4.0-in3-acp-server`. **No action required yet** — this is the contract to design
against, not a request to change anything today.

---

## The problem it solves

Our sub-agent dock deliberately keeps sub-agent traffic **out of the main transcript**. That
separation is a product differentiator — the memo on it is explicit that `agentId`-tagged
content goes to the dock and pop-out only.

A generic ACP host has no dock. It renders whatever `session/update` it receives. So the
v5.0 boundary forced a choice:

| Option | Cost |
| --- | --- |
| Send sub-agent output as ordinary updates | Generic hosts render it — but our dock loses the separation |
| Send it only in `_meta` | Our dock works — but a generic host silently drops the content |

**Neither. Both readers get served:** the content goes out as an **ordinary
`session/update`**, and the envelope carries `_meta` identifying it as sub-agent traffic.
A generic host renders it inline and loses nothing; our client reads `_meta` and routes it
to the dock instead of the transcript.

ACP makes this safe by design — `_meta` is *"reserved … to attach additional metadata"* and
implementations *"MUST NOT make assumptions about values at these keys."*

---

## The contract

`_meta` sits on the **`SessionNotification` envelope**, not on the update variant. The
variants have no `_meta` in the schema — a common thing to get wrong.

```jsonc
{
  "sessionId": "…",
  "update": {                                   // ← ordinary, renders anywhere
    "sessionUpdate": "agent_message_chunk",
    "content": { "type": "text", "text": "from a sub-agent" }
  },
  "_meta": {                                    // ← ours; safe for others to ignore
    "copilotCliChat.agentId": "task-7",
    "copilotCliChat.subagentEvent": "message"
  }
}
```

**Keys are namespaced under `copilotCliChat.`** `_meta` is a shared extension point; a bare
`agentId` would collide with any other agent that had the same idea. There is a test
asserting every key we emit contains a `.`.

### Values of `copilotCliChat.subagentEvent`

| Value | Emitted when | Extra keys |
| --- | --- | --- |
| `start` | a sub-agent begins | `copilotCliChat.agentName`, `copilotCliChat.agentDisplayName` |
| `message` | sub-agent output | — |
| `reasoning` | sub-agent thinking (`agent_thought_chunk`) | — |
| `complete` | it finishes or fails | `copilotCliChat.status` (`complete` \| `failed`) |

**`agentId` keeps its existing meaning** — it equals the spawning task's `toolCallId`, the
same value the dock already keys on. No new identifier was invented.

### The invariant, and it is tested

**Main-transcript output is never tagged.** Ordinary assistant text, reasoning and tool
calls carry no `_meta`. If they did, everything would drain into the dock and the transcript
would empty. Mutation-checked: tagging ordinary output fails a test.

And the reverse: **the transcript reads correctly with `_meta` stripped.** There is a test
that deletes `_meta` and asserts the update is still a well-formed, renderable chunk.

## What this means for Lane B — eventually, not now

Today the extension routes to the dock by reading `agentId` off the **event payload**
(`extension.ts` assigns a colour per `agentId` and rides it on the payload). Under v5.0 the
same information arrives on `_meta` instead, because the payload has become a protocol
message.

So the change, when it comes, is **where you read the tag, not what you do with it**:

```
today:  event.agentId            → dock
v5.0:   notification._meta['copilotCliChat.agentId'] → dock
```

Your note that "it will need a change how we handle messages today, but we're going to need
to do that anyway" is exactly right, and this is the shape of it.

**Nothing is asked of v3.13.0.** IN-4 (webview as AHP client) is where this lands, and it is
deliberately held until AHP is nearer 1.0. The value of writing it down now is that
`ChatSessionHost`'s message handling is being shaped **this week**, and a routing seam that
can take its tag from either place costs nothing today and a refactor later.

### Concretely, the one thing worth doing now

When Task 5 routes the 75 call sites through the host, **do not hard-code
`event.agentId` as the dock's routing key at each site.** One accessor — "is this
sub-agent traffic, and whose?" — behind the host's narrow slice means the v5.0 switch is one
function, not seventy-five.

That is the same reasoning as `.manager` staying private: declare the question you are
asking, not the field you happen to read it from today.

## Open, and genuinely undecided

**Lifecycle events currently carry human-readable filler text** — `"Started Explorer."`,
`"Explorer finished."` — because an `agent_message_chunk` needs *some* content and a generic
host would otherwise render an empty bubble. Our dock will ignore that text and use `_meta`.

That is defensible but not obviously right. The alternative is to emit no lifecycle updates
at all and let the dock infer open and close from the first and last tagged message, which is
quieter on a generic host but loses the sub-agent's name and final status.

**If you have a view from the dock side, it is worth having before IN-4.** You know better
than I do what the dock needs to open a card cleanly.
