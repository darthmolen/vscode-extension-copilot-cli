## 1. What IN-3 is

We stop being only a client and become an **agent other hosts can drive**. Direction is everything,
and it is the opposite of the abandoned `feature/4.0-acp-migration` branch:

```text
DEAD (abandoned):  our client ──ACP──▶ copilot --acp     ← cli#1574 / cli#1607 live here
IN-3 (this):       host ──ACP──▶ our agent ──SDK──▶ CLI  ← and cannot reach here
```

`copilot --acp` is **never invoked**, so those two CLI defects are off our path entirely. Do not let
anyone re-conflate these; it has already cost one abandoned branch.

Value is outcome-independent: VS Code opens up → we plug in; it does not → any AHP host or Zed drives
us; neither → IN-9 (our own host) consumes it unchanged.

## 3. Non-obvious facts that cost real time to establish

**Re-deriving these is the main risk of a cold pickup.**

1. **Never pass a method name as a string literal — use `acp.methods`.** There is no
   `client.sessionUpdate()`. `client.notify(method, params)` has an escape-hatch overload that
   swallows every mistake: a **typo'd string compiles clean** under `tsc --strict`. The SDK exports
   typed constants and its own example uses them —
   `cx.notify(acp.methods.client.session.update, …)`. A typo on the constant is `TS2551`.
   → **Use the constants; no facade required.**
2. **`initialize` is not guaranteed to run.** `buildSession().start()` issues `session/new` only.
   Handlers must work uninitialized. This is security-adjacent: `clientCapabilities` gates whether we
   forward to `session/request_permission` or fall back to `approveAll`, and branching on an unset
   capability **silently auto-approves** rather than crashing — the same failure class as cli#1607.
   → Default to the schema's own `fs: { readTextFile: false, writeTextFile: false }`; let
   `initialize` **upgrade** it, never require it.
3. **Cancellation is an `AbortSignal`** on the handler context (`signal`), not a notification to
   correlate. Ergonomics only — the wire still carries cancel as a notification, so model it
   **fire-and-forget**, never a request awaiting a reply.
4. **The handler context is `{ params, requestId, signal, client }`.** Not `context`.
5. **The client drives**: `clientApp.connect(agentApp)`. The `AgentConnection` from
   `agentApp.connect(...)` is the mirror image, for calling clientward.
6. **ESM/CJS is settled.** The SDK is `"type": "module"`; our extension is CJS. Not a conflict — the
   agent is **its own process**, and an ESM entry point `require()`s our compiled
   `out/sdkSessionManager.js` and the S4 `CopilotClientProvider` (spike steps 5a/5b). The agent never
   enters the extension bundle.
7. **ACP multiplexes**: every request carries `sessionId` (`PromptRequest`, `CancelNotification`,
   `LoadSessionRequest`), so one agent connection serves N sessions. IN-3 therefore needs an
   id→manager map.

### Process lesson — do not skip this

**Three consecutive wrong guesses from the `.d.ts` alone** (`conn.initialize`,
`conn.agent.initialize`, `client.sessionUpdate`). Each looked right in the declarations and did not
exist at runtime, because the typed surfaces are not what `connect()` and the handler context hand
you. What worked was dumping the live object:

```js
const keys = o => [...new Set([...Object.keys(o), ...Object.getOwnPropertyNames(Object.getPrototypeOf(o) || {})])];
```

Straight-to-TDD would have been three rounds of red tests against a misremembered API — debugging our
own mocks instead of the protocol.

## 4. Next step — the walking skeleton (TDD, not started)

Smallest thing that makes the protocol risk real, before the other four scope items land on top of an
assumption.

**Test in-process.** `clientApp.connect(agentApp)` needs no transport, no subprocess and no CLI, so
the protocol surface is unit-testable **against the protocol authors' own client**. That is the cheap
tier and most of IN-3 belongs there.

Suggested first RED cycles:

1. `initialize` returns our protocol version and advertised capabilities.
2. **Capability default holds when `initialize` never ran** — drive `session/prompt` without
   `initialize` and assert deny-by-default (fact 2 above). This is the invariant most likely to be
   broken later by someone "simplifying".
3. `session/new` creates a manager and returns its id; a second call returns a *different* id and
   both remain addressable (fact 7).
4. `session/prompt` maps one manager emitter to one `agent_message_chunk` through the typed facade.
5. The typed facade is the only place `'session/update'` appears (guard test, S2-palette pattern).

Only then: real prompt through `SDKSessionManager`, then `session/cancel` via `signal`, then the
remaining scope items.

**Also in this ticket** (from the ticket's own §"What Phase 0 established"): remove
`sdkSessionManager.ts`'s static fallback to `createVSCodeHostBridge` and split `vscodeHostBridge.ts`
out — see [the memo](../backlog/hostbridge-split-and-fallback-seam.md). The decoupling is currently
true but not enforced by the module graph.

## 7. Standing repo rules that bite here

- **The suite is flaky.** A single red run proves nothing — re-run the failing file alone. **A single
  green run proves nothing either.** See CLAUDE.md.
- **Squash-merge breaks ancestry checks.** `git merge-base --is-ancestor <sha> main` reports a false
  negative for anything squash-merged. Verify by **content** (`git diff --stat origin/main <sha>`)
  before resetting or force-pushing. This bit twice.
- **`gh pr edit` is broken on this repo** — it queries deprecated `projectCards` and **silently
  aborts the edit** while printing only a warning. Use
  `gh api -X PATCH repos/.../pulls/N -F body=@file` instead.
- **Never `git add -A`** here — the sibling lane's untracked files land in your commit. Stage
  explicitly.
