## Context

The extension has one chat surface — the sidebar `WebviewView` — driven by one module-level
`sessionManager`, one `BackendState` singleton, and one `ExtensionRpcRouter`. The valuable pattern
this exists to enable is a long task running in the sidebar while a second conversation happens in an
editor tab. That needs a session to be viewable in a tab or the sidebar interchangeably, which means
"a chat surface" has to become a thing you can have more than one of.

Slice 2a (`CopilotClientProvider`) was reassigned to Lane A and **landed as spine step S4** (`7d0a827`).
It took one optional trailing constructor parameter, so `extension.ts` needed no edit and nothing Lane
B owns was touched. S4 is the declared sync point: **both lanes rebase on `main` before this starts.**

### Decisions taken

| Question | Decision |
| --- | --- |
| Concurrency | Both sessions live, **one shared `CopilotClient`** (one CLI process), via S4's provider |
| Session ↔ surface | **One session, one live surface.** Never mirrored |
| New Tab | Opens a **new** session, not the current one — active file seeded |
| `/btw <question>` | New session in a tab, pre-seeded — i.e. New Tab + send. Does **not** inherit history |
| Fork | Opens the fork in a tab; sidebar stays on the parent |

One-session-one-surface is load-bearing. It dissolves the move-vs-mirror question: no scroll
divergence, no double streaming, no second router per session, no shared-transcript reconciliation.

## Prerequisites — neither is optional, both were review criticals

### P1 — The concurrency contract for two live sessions

**This is the headline use case and it is currently a data-loss path.** `FileSnapshotService` is
instantiated **per manager** ([sdkSessionManager.ts:431](../../src/sdkSessionManager.ts#L431)), and
snapshots are captured by path before tool execution. Two hosts means two independent snapshot stores
over one shared workspace. If both sessions touch the same file, accepting one session's diff writes a
snapshot-derived result that silently discards the other's edits. Permissions compound it — both
sessions run `onPermissionRequest: approveAll`, so nothing prompts.

Decide and write down one of:

- a workspace-level write lock;
- a "another session is editing `<file>`" warning surfaced in **both** surfaces;
- an explicit, documented decision that concurrent writes are the user's problem, with a warning on
  the second surface.

Whichever is chosen, it ships with a verification step in which **both sessions edit the same file**.
Do not ship the fork-opens-a-tab task without an answer here.

### P2 — Tool messages corrupt any replayed transcript

[chatViewProvider.ts:687-696](../../src/chatViewProvider.ts#L687-L696) persists every tool call to
`backendState` as an assistant message whose content is `description || name || 'Tool execution'`,
with `type: 'tool'` and `status: 'running'`. On replay,
[main.js:605-614](../../src/webview/main.js#L605-L614) rebuilds each entry as
`{role, content, timestamp}` — **dropping `type`, `toolName` and `status`.** Every tool call returns
as a plain assistant bubble reading "Tool execution", frozen at running.

Observed live: `[Init] Sending 61 messages to webview` producing a wall of identical bubbles.

This is the same replay path `registerWebviewPanelSerializer` uses to restore a chat tab, so tab
restore inherits it wholesale. Fix the round-trip — carry `type`, `toolName`, `status` through init —
rather than suppressing the symptom.

## Entry points

Three verbs, each mapping to one mechanism. Keeping them distinct is what makes this teachable:

| Verb | Result |
| --- | --- |
| **New Tab** | Empty **new** session in a tab, active file seeded |
| **`/btw <question>`** | New session in a tab, pre-seeded with the question — i.e. New Tab + send |
| **Fork / Fork from here** | A **copy** of the current session in a tab |

`/btw` deliberately does **not** inherit the parent's history — that is what fork is for. Which makes
it nearly free: once New Tab exists, `/btw` is New Tab plus one `sendMessage`.

### Placement

- **`editor/title`** — a `$(split-horizontal)` action, tooltip *Copilot CLI: New Tab*.
  **Do not use `when: editorFocus`.** The existing `openChat` icon uses it and is therefore invisible
  whenever focus sits in the chat webview — which is most of the time you would reach for it. It reads
  as the icon randomly not existing. Use `editorIsOpen`, or no `when` at all, which is why Claude
  Code's equivalent is always present.
- **`view/title` on `copilot-cli.chatView`** — because when you want a second session you are usually
  already in the chat, not in a file. **Repurpose rather than add:** the existing `newSession` `$(add)`
  here duplicates the webview's own `+` beside the session dropdown. Make the toolbar one *New Tab*
  and leave the in-panel `+` as new-session-in-sidebar. That removes a duplicate instead of adding a
  third add-button.
- **`refreshPanel`** — drop from `view/title` (palette-only). It exists to paper over P2 and triggers it.
- **Per-tab actions** — scope with `when: activeWebviewPanelId == 'copilotChatPanel'` for things the
  sidebar cannot have (⑂ Fork This Session, ↩ Move Back to Sidebar).
- Active file seeding honours the existing `copilotCLI.includeActiveFile` setting; it does not force it.

Related chrome defects are filed separately as
[chat-toolbar-cleanup-and-new-session-reset.md](../backlog/chat-toolbar-cleanup-and-new-session-reset.md).
Items 1 and 3 there (the duplicate `+`, the `editorFocus` gate) are worth doing **before** Task 8 so
this isn't designed around known-bad chrome.

**End to end**, in the Extension Development Host:

1. Start a long task in the sidebar; open a New Tab — both stream concurrently, output lands in the
   right surface.
2. **Both sessions edit the same file** — P1's contract holds (blocked, warned, or resolved). Not
   optional; this is the scenario the feature exists for.
3. Sub-agent traffic from the tab's session renders in the tab's dock, not the sidebar's.
4. Close the tab → session survives; reopen → history intact, **no wall of "Tool execution"** (P2).
5. Reload the window → tab restored by the serializer; nothing double-inits or re-resumes (Task 6).
6. `/btw <question>` → new tab, pre-seeded, parent untouched and still streaming.
7. One CLI process, not N (`ps` for the copilot node process).

### Issues

#### Critical (Must Address Before Implementation)

**C1 — P1 has no decision.**
The plan lists three concurrency options but commits to none:
> "Decide and write down one of: workspace-level write lock / warning in both surfaces / explicit documented decision that concurrent writes are the user's problem."

This is the blocker the plan itself declares ("Do not ship the fork-opens-a-tab task without an answer here"). The plan must pick one and describe its implementation before Task 9 opens — or before Task 4, since `ChatSessionHost` will need to enforce whichever policy is chosen. Leaving it as "decide later" means Task 9 inherits an open design question and the implementer may ship the wrong thing.

**Suggested fix:** Add a "Concurrency decision" row to the Decisions table at the top: pick the warning approach (lowest complexity, matches the "thoughtful" design principle — surface the conflict rather than silently block or silently allow), and describe: which service owns the check, which event/RPC message surfaces it to the webview, and what both surfaces show.

---

**C2 — P2 fix lacks schema specificity.**
The plan correctly diagnoses the bug but stops at "fix the round-trip — carry `type`, `toolName`, `status` through init." The actual fix requires changes in at least three places:

1. The `init` RPC message payload type in `src/shared/messages.ts` — `Message[]` currently uses `{role, content, timestamp}`; needs `type`, `toolName`, `status`.
2. `chatViewProvider.ts` `sendInitData` (wherever it serialises `backendState.getMessages()` for the init payload) — must pass the full `Message` shape.
3. `main.js` `handleInitMessage` — must forward `type`, `toolName`, `status` to `eventBus.emit('message:add', …)` so ToolExecution renders correctly.

Without naming these three change sites, an implementer following the plan risks fixing only one or two. The task description should call out all three explicitly.

### Recommendations

1. **Resolve P1 in the plan, not in the PR.** The concurrency decision shapes `ChatSessionHost` (Task 4) — make it before Task 4 opens, not at Task 9.
2. **Expand the P2 fix into a concrete three-point checklist** (messages.ts schema, serialize path in chatViewProvider, deserialize path in main.js). P2 is the one bug that is guaranteed to manifest on the very first tab-restore test.
3. **Consider whether Task 3 and Task 4 should merge.** If the shared state becomes a parameter injected into `ChatSessionHost`, there is no intermediate state where a restructured `BackendState` exists but `ChatSessionHost` doesn't. Keeping them separate is fine if the intermediate state genuinely compiles and tests pass; merging them avoids a possibly awkward halfway commit.
4. **Add a negative-case end-to-end test:** "reload with zero prior tab sessions" and "open a tab with no active file" (should seed with workspace root or nothing, not crash). The verification list covers the happy path well but misses the serializer cold-start case.
