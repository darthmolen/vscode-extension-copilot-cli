# v3.13.0 — Chat in a Tab

**The largest refactor since 1.x → 2.x**, and the first one where the visible feature is the smaller
half. 65 commits, ~5,300 lines added and ~1,550 removed across `src/`, with the test suite growing by
slightly more again — 2,127 tests, up from 1,912.

This document is the durable record: what a user gets, and what the codebase got that made it
possible. The plan that drove the second half is archived at
`planning/completed/v3.13.0-p3-host-owned-managers.md`; the rest of the history is beside it.

---

## Part 1 — What you get

### Chat in an editor tab

`Copilot CLI: New Chat in Editor Tab` opens a full chat as an editor tab: same UI, same slash
commands, same sub-agent dock. Not a preview pane, not a cut-down view — the identical surface the
sidebar renders.

**A New Tab is a *new* conversation.** It does not mirror the sidebar and it does not inherit its
history. That is a deliberate decision, not an accident of implementation: the gesture said *new*, so
neither `copilotCLI.resumeLastSession` nor the most-recent-session heuristic gets a vote.

**Two conversations run at once, and stay separate.** Ask the sidebar a long question, open a tab,
work on something else. Both stream simultaneously and each renders only its own output — messages,
reasoning, tool chips, diffs and sub-agent traffic all route to the surface that owns the session.

**A tab survives a window reload.** Reopen VS Code and the tab comes back showing the same
conversation, with its transcript replayed from the session's own event log. If the session it was
showing has meanwhile been taken by another surface, or the state is unreadable, the *tab still comes
back* — with a fresh conversation in it. VS Code restored that tab because you had it open; emptying
it is reasonable, closing it is not.

**No freshness gate.** A tab pinned to a session is a standing instruction. Come back after a week and
it still restores that conversation. (For comparison: Claude Code's extension rebinds only within ten
minutes and otherwise gives you an empty tab. We deliberately do the opposite.)

### Restored transcripts are real again

Reopening or switching to a session used to render every past tool call as an identical grey bubble
reading *"Tool execution"*, frozen at `running`. Session history is now projected from the CLI's own
event log, so a replayed tool shows its real name, its real arguments and whether it actually
succeeded — the same chips the live path draws.

This also fixed a subtler bug: session-switch and webview-reload used to read *different* sources and
produce *different* histories for one session. There is now one projection and one init path.

### Smaller things that came with it

- **Each surface's session dropdown shows its own session.** Previously any surface without a session
  yet displayed whichever session was touched most recently — someone else's — because a native
  `<select>` falls back to its first option.
- **The active file and the session list reach every surface**, not just the sidebar.
- **Sub-agent traffic stays in its own session's dock**, so two conversations running sub-agents do
  not interleave.
- **Sub-agent tool rows say what the tool did** — `skill`, `sql` and `task` previously rendered
  without their arguments.

### Three ways in, one mechanism each

Keeping them distinct is what makes them teachable:

| | |
| --- | --- |
| **New Tab** | An empty **new** session in a tab, seeded with the file you were looking at |
| **`/btw <question>`** | A side question in a new tab — New Tab plus one send, literally |
| **Fork** | A **copy** of this session in a tab; you stay on the parent |

`/btw` deliberately does not inherit history. The point of a side question is that it is *not* part of
the conversation you are in, and carrying the transcript across would spend exactly the context you
were trying to protect. That is what fork is for.

The seeded file is **pinned** to that tab. It honours `copilotCLI.includeActiveFile` — someone who
turned that off did not ask for it back — but the click says which file *this* tab is about, and
rewrites no setting. Pinned rather than followed, or the seed evaporates the moment you click into
another file to check something.

### A tab that closes does not leave a session running

Closing a chat tab used to dispose the surface and leave its CLI session alive for the life of the
window. Open and close tabs over a day and that is a live session each, with no UI.

Killing it on close is the other extreme — it would abort a task you set running and merely stopped
watching. So an orphaned conversation is **on a countdown that any reattach cancels**: it winds down
now if it is idle, at the end of its turn if it is working, and not at all if you come back to it.
Reselecting a closed tab's session from the dropdown *is* coming back to it.

### Your choices survive

Three of them, all the same shape — a gesture that was honoured and never written down, so a standing
default won it back at the next reload:

| Gesture | What used to win |
| --- | --- |
| Switching model mid-session | `copilotCLI.model`, on the next resume |
| Switching to an older session and reading it | the most-recent-by-mtime heuristic |
| *New Tab* on a specific file | `copilotCLI.includeActiveFile` |

Each is now recorded beside the thing it belongs to — the model in `session-model.txt` next to the
session, the sidebar's session in this window's state, the file on the tab that was opened. And each
is **scoped to what was actually expressed**: recording which session you chose does not override
`copilotCLI.resumeLastSession`, which says *whether* to resume and stays yours to set.

### Half a conversation is no longer listed as a whole one

Plan mode starts a second CLI session, and it appeared in the dropdown as an ordinary conversation.
Measured before the change: **38% of this workspace's rows** and 22% of the whole session store. A
plan session now sits directly under the conversation it belongs to, labelled `↳ Plan: <parent name>`
— named after its parent, because a native `<select>` shows only the selected option once collapsed,
so `↳ Plan` alone would read as nothing.

## Part 2 — What the codebase got

The feature needed one thing the extension could not do: **have more than one chat.** Everything below
is what it took, and most of it is worth more than the tab.

**Three things to be proud of, if it comes to three:**

1. **`chatViewProvider.ts`: 1,011 lines → 38.** A god object became a registration.
2. **Punch in, punch out.** Four attach/detach seams, so every layer can be swapped while the ones
   above and below it keep running.
3. **The tests test behaviour now.** Not because the rule was written down — it already was, and was
   ignored — but because a refactor finally broke enough of them to force the issue.

### The shape of the problem

"A chat session" used to be three module-level globals in `extension.ts` — a `sessionManager`, a
`BackendState` singleton, and a set of slash-command services built during handler registration. That
works exactly as long as there is one surface, and stops the moment there are two. Every value that
should have been *"this conversation's"* was *"the window's"*.

### The shape of the answer

```
window   WorkspaceRuntimeState     active file, session list, MCP state — shared, observable
         CopilotClientProvider     the CLI process
  host   ChatSessionHost           one conversation: its id, its state, its manager, its wiring
           └── ChatSurface         what renders it — at most one, never mirrored
                 └── ChatWebviewSlot   sidebar view or editor panel; four members differ
```

**`ChatSessionHost`** owns a conversation end to end and exposes it as verbs — `prompt`, `cancel`,
`switchModel`, `compact`, `rename`, `selectAgent`, `reloadAgents`. Its manager is a true `#private`
field, not a TypeScript `private`, so no JavaScript call site can reach through it. That is not
fussiness: v4.0 replaces the manager with a session handle on the far side of a process boundary, and
75 call sites were rerouted through the host specifically so they survive that move. A guarantee that
only holds while everyone compiles is not the guarantee that was wanted.

**`ChatSessionRegistry`** answers *"is this session live in this window?"* without starting anything —
the question the serializer and the attach flow both need, and which nothing could answer before.
Hosts are held from birth rather than from their first session id, because a host whose CLI never
starts has no id and would otherwise be invisible to cleanup on exactly the path where something
already went wrong.

**`ChatWebviewSlot`** is the seam that made one surface class serve both containers. Measured before
deciding: the old provider touched its VS Code object four times in ~600 lines, and every one was on
`.webview`, whose type is *identical* for a view and a panel. The difference is four members — how you
show it, how it reports visibility, and what its disposal means — not a class.

### `chatViewProvider.ts`: 1,011 lines → 38

That file was the extension's god object. It held the webview, the RPC router, the slash-command
services, MCP status building, image resolution, the file picker, mermaid export, the transcript
writers and the HTML — and, being the only thing that owned a webview, it had quietly become the
place anything webview-adjacent went.

It is now the sidebar's registration with VS Code and nothing else:

```ts
export class ChatViewProvider implements vscode.WebviewViewProvider {
    public static readonly viewType = 'copilot-cli.chatView';
    constructor(private readonly surface: WebviewChatSurface) {}

    public resolveWebviewView(webviewView, _context, _token): void {
        this.surface.attach(new SidebarSlot(webviewView, ChatViewProvider.viewType));
    }
}
```

The 973 lines did not vanish — most became `webviewChatSurface.ts`, which is *N instances* rather than
one. What actually left is the assumption baked into every one of them: that there is exactly one of
this thing, so it may as well own everything.

### Punch in, punch out

The property that makes the rest work. **Four attach/detach seams**, each one symmetrical, each one
letting a layer be replaced while its neighbours keep running:

| Seam | Punch in | Punch out | What it buys |
| --- | --- | --- | --- |
| container ↔ surface | `surface.attach(slot)` | slot disposal | VS Code can tear down and re-resolve the sidebar view without the conversation noticing |
| surface ↔ host | `host.attachSurface()` | `host.detachSurface(surface?)` | a tab can close and the session survives; reopening reattaches instead of restarting |
| manager ↔ host | `host.attachManager()` | `host.detachManager()` | a host outlives its managers — every restart and session switch builds a new one |
| host ↔ registry | `registry.create()` | `registry.disposeHost()` | a host that never got a session id is still reachable for cleanup |

Two details carry most of the weight. `attachManager` **replaces** rather than adds, because a host
sheds managers repeatedly and each restart would otherwise double every message on screen. And
`detachSurface` is **identity-guarded** — a surface already replaced by another cannot detach its
successor on the way out.

`ChatWebviewSlot.closingEndsSurface` is where the asymmetry lives: VS Code disposes the sidebar view
whenever its container is hidden and re-resolves it later into the same surface, whereas a closed tab
is gone. That used to be a comment (*"Don't dispose `_view` — VS Code owns the sidebar view
lifecycle"*). It is now a flag the code branches on, so no call site has to remember which kind of
container it is holding.

**Window state is observed, not pushed.** `WorkspaceRuntimeState` announces changes and surfaces
subscribe. The alternative — a fan-out loop at each call site — is the shape that had already produced
three hand-built init payloads and two argument formatters in this codebase.

### Two ideas that did most of the work

**One truth, in one place.** The recurring defect all cycle was a single fact computed or built in two
places and kept in step by memory. Three separate init payloads. Two argument-preview formatters that
were *identically* wrong, so nothing looked inconsistent. A start decision made twice from different
inputs, where the second silently won and quietly mirrored one conversation into two surfaces. Each
fix was the same move: collapse to one builder, one decision, one projection — and where two
representations genuinely must exist, bind them with a test that compares *values*, not field names.

**Intentional actions are treated intentionally.** A setting is a standing default; a gesture is a
stated intent; the gesture wins **and gets recorded**, scoped to what it actually expressed. Now a
principle in `CLAUDE.md` with a three-step check, because it turned up four separate times — *New Tab*
versus `includeActiveFile`, a mid-session model switch versus `copilotCLI.model`, a deliberate session
switch versus most-recent-by-mtime, and restoring a tab versus the resume heuristic.

### The tests test behaviour now — and the rule alone did not do it

The suite is 2,127 and **it went down before it went up.** Forty-four assertions that read production
files and checked for the presence of a *string* were removed, on top of ten whole tests deleted
earlier in the cycle. They could not fail for a real reason, they broke on correct refactors,
and they reported coverage a comment would satisfy.

The uncomfortable part is worth writing down, because it is the actually useful finding:
**this was already prohibited, in writing, and kept happening anyway.** `CLAUDE.md` has said
*"Was the test matching against a string, comment, or dead import? **Delete the test.** It was never
verifying anything"* for a long time, with a worked example. The tests kept being written — by AI,
including by me, in sessions that had that file loaded.

So the honest lesson is not *"don't write source-scan tests."* It is:

> **A rule in a document is not a gate.** Nothing in the loop ever failed because of it. Every one of
> these was removed either because a legitimate refactor broke it, or because someone spent an
> afternoon deliberately hunting them. Neither is enforcement.

What made them *look* valuable is the same thing that makes them easy to write: a source scan always
passes on the first run and never flakes, so it reads as a cheap green test. A behavioural test costs
more to write and can fail. Under any pressure to move, the cheap one wins — and an instruction in
prose does not change that arithmetic.

Two things did change it. The refactor broke them in a batch, which converted an abstract rule into a
concrete pile of red. And the replacement was written *first*, so the question stopped being "should I
delete this" and became "what does this actually check" — which, for message-delta streaming, turned
out to be *nothing else in the suite*, and the behavioural replacement promptly covered two guards the
scans had never seen. A gate that fails is tracked in
[`planning/backlog/source-scan-tests.md`](../planning/backlog/source-scan-tests.md).

The related lesson from the same cycle: **the defects that mattered were not found by the suite at
all.** Two startup races survived 2,043 unit tests and three consecutive clean runs, and gave
themselves up in a log within minutes of the first live run — because both need two surfaces starting
at once, and only a window reload does that. Neither would have shown in a screenshot either; the tab
*looked* right.

Every task in this line is therefore verified in the Extension Development Host with the Output
Channel saved to `tests/logs/server/`, and the per-surface log lines now carry which surface they came
from — because with N surfaces, attribution is the whole question.

### The global that answered every question wrong

`extension.ts` held one `sessionManager`. With one surface that meant *"the window's session"*; with
two it means *"whichever session started last"*, and three live defects came straight out of it —
including one you could see: **the dropdown and the plan-mode toggle in a tab drove the sidebar.**

The first two were patched at the seams. The third could not be, because the seam *was* the global.

So every read of it was classified, and there was exactly one bucket:

| Reads | What they actually wanted |
| --- | --- |
| plan mode, stop, fork, the model list, attachment validation, the MCP lists | the session this surface is showing |
| `dispose()` in `deactivate` | **all** of them — which it did not do |

Not one wanted *"a thing this window has, once"*. The one that looked window-scoped was the opposite:
it disposed a single manager, so every other conversation's CLI leaked — already true on a session
switch, one worse per tab.

It is **deleted**, not deprecated, so "reads the wrong session" stops being expressible. And the fix
for the visible defect was not a resolver. Tracing `/plan` typed in a tab, the signal arrives at
`registerChatHandlers` with its identity fully intact — one router per surface, closed over one host —
and `executeCommand` threw that away on the very next line. A resolver would have been machinery to
reconstruct what we chose to discard. The fix was to stop discarding it.

### Kept portable on purpose

`ChatSessionHost`, `ChatSessionRegistry`, `sessionStartPlan`, `sessionBootstrap` and
`sessionTranscriptBuilder` import neither `vscode` nor the SDK. Two reasons, and both have already
paid: they are requirable from plain mocha, which is why the multi-surface behaviour is testable at
all; and v4.0 moves this layer behind a protocol boundary, where anything holding a `vscode` import
would have to be rewritten rather than moved. The host's verbs are named for ACP's session methods for
the same reason — `cancel` returns `void` because on the wire it is a notification, and a
`Promise`-shaped cancel would not survive the crossing.
